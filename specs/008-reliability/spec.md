# Feature Specification: 信頼性と堅牢性（版 1.26）

**Feature Branch**: `008-reliability`
**Created**: 2026-10-13
**Status**: Draft
**Input**: 利用者「今開発中の SW で、アーキテクチャ的に問題ないかどうか、セキュリティ的に問題ないかどうか、つまり信頼性と堅牢性をチェックしたい」→ 3 つの観点で点検（[decision.md](decision.md)）→ 提案した順（再現の守り → Worker とメモリ → 写真を替えたときの順番 → セキュリティの細かい点と CSP → 片付け）に「OK」。
言葉は [docs/GLOSSARY.md](../../docs/GLOSSARY.md)（信頼性・堅牢性のチェック、再現の守り）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 気に入った絵がいつまでも同じに出る (Priority: P1)

保存したレシピと同じ写真から、いつでも同じ絵が出る。コードを直して絵が変わるなら、テストが止めて知らせる。版が合わず再現できないときは、どの版で開けば再現できるかが分かる。

### User Story 2 - 大きな写真でも落ちず、止まったままにならない (Priority: P1)

CPU の多い PC で大きな写真を使っても、メモリを使いすぎて落ちない。描画の処理が落ちても、理由が出て次の操作で描き直せる。AI が返ってこなくても、AI なしで描き続ける。

### User Story 3 - 写真を続けて替えても、最後に選んだ写真で描かれる (Priority: P2)

### User Story 4 - 壊れた・細工したファイルでも、理由が出て作業が消えない (Priority: P2)

## Requirements *(mandatory)*

### 再現の守り

- **FR-801**: 7 つの世界それぞれ（別案 0〜5）と、囲みのある「主題」を、決まった写真（`docs/reference/decoded-source.png`）・日時・小さな大きさ・AI なしで描いた画素のハッシュを記録し、
  テストで毎回確かめる。描画は画面と同じ経路（Worker の描画関数）を通す。世界の版（`SPACE_ALGORITHM_VERSIONS`）が記録時と同じなのに絵が違えば失敗し、
  「変えるなら世界の版を上げてから記録し直す」と出す。記録は道具 `tools/world-hashes.ts` で行う
- **FR-802**: レシピにアプリの版と commit（`app: { version, commit }`）を書く。版が合わず断るとき、レシピにそれがあれば「ver X（commit Y）で保存された作品です。その版で開くと再現できます」と出す。
  `app` がない古いレシピも今までどおり読む
- **FR-803**: 世界の版の照合は今までどおり全部の一致で行う（世界ごとに絞ることはしない。理由は decision.md）

### Worker とメモリ

- **FR-804**: 描画用の Worker は 2 つまで（Worker が使えないときは画面の中で 1 つ）。プレビューに使うのは 1 つまでとし、もう 1 つを書き出しのために空けておく
- **FR-805**: Worker が落ちたら（`error`・`messageerror`）、その仕事を「描画の処理が止まりました（メモリ不足の可能性があります）。もう一度操作すると描き直します」で失敗にし、
  Worker を作り直して写真を送り直す。使える Worker の数は減らない
- **FR-806**: Worker は写真を 2 枚まで持つ（写真を替えた直後でも、前の写真の書き出しを最後まで描ける）
- **FR-807**: AI の見分けに時間の上限（60 秒）を設け、超えたら「AI が時間内に終わりませんでした（推定で描画）」として AI なしで続ける
- **FR-808**: Worker の準備に失敗したら、画面の中で描く方式に切り替えて知らせる（操作を黙って捨てない）

### 写真を替えたときの順番

- **FR-809**: 写真を続けて選んだら、最後に選んだ写真だけを使う（先に選んだ写真の読み込みが後に終わっても上書きしない）
- **FR-810**: Worker へ写真を送るのは、状態の更新と同じ順番待ちの中で行う。写真を替えた直後に「source N is not loaded」の失敗を出さない
- **FR-811**: レシピの読み込みは、確かめた写真と当てはめる時の写真が同じときだけ当てはめる。「読み込みました」は当てはめが終わってから出す。途中の失敗は理由を出す

### セキュリティの細かい点

- **FR-812**: ビルドした単一 HTML に CSP（`connect-src` などで外への通信をブラウザ側でも止める）を入れ、今の JS での遮断と二重にする。開発サーバーには入れない。file:// で AI と描画が動くことを確かめる
- **FR-813**: 写真は読む前にファイルの大きさ（20 MiB）で断る。読み込み後の幅と高さをもう一度確かめる。縦か横が 32767 px を超える画像は「画像の縦か横が長すぎます」で断る
- **FR-814**: レシピのファイルは 1 MiB まで。入れ子が深すぎるもの・読み込み中の例外は、理由を出して断る（黙って失敗しない）
- **FR-815**: 絵の枠の外にファイルを落としても、ブラウザがそのファイルを開かない（ページ全体で既定の動作を止める）
- **FR-816**: 囲みは主ボタン（左ボタン）だけで始める。取り消された操作（`pointercancel`・`lostpointercapture`）では囲みを作らない。ほとんど動いていない操作（絵の幅の 1% 未満）は囲みにしない

### 片付け

- **FR-817**: レシピの `output.qualityMode` は実際の書き出しどおり `standard` を書く（3×3 の高品質は空間モードでは使っていない。読み込みは両方受け付ける）。状態の `exportQuality` はなくす
- **FR-818**: 消したモードの残り（使われていないコード・資料）を消し、古い文書の冒頭に「006 で取り下げ」と書く。README の版を合わせる
- **FR-819**: 開発用の依存の既知の弱点のうち、版を上げて直せるもの（source-map-js）は直す

### 変えないもの

- **FR-820**: 描かれる絵（Phase 9 の 16 枚と FR-801 の記録）・外部通信 0 件・端末内処理は変えない。版は 1.26 にする

## Success Criteria *(mandatory)*

- **SC-801**（FR-801）: 世界の記録のテストがあり、描画の数値を 1 か所変えると失敗する（確かめてから戻す）
- **SC-802**（FR-802）: 保存したレシピに `app.version`・`app.commit` がある。版の違うレシピを読むと、その版が案内に出る。`app` のないレシピも読める
- **SC-803**（FR-804〜FR-808）: unit: Worker は 2 つまで、プレビューは 1 つまで、落ちた Worker は作り直されて次の仕事が描ける、写真は 2 枚まで持つ、AI の時間切れで AI なしになる
- **SC-804**（FR-809〜FR-811）: e2e: 2 枚続けて選ぶと最後の写真が出る。写真を替えた直後に失敗が出ない
- **SC-805**（FR-812〜FR-816）: ビルドに CSP がある（file:// で描け、通信 0 件）。大きすぎるファイル・長すぎる辺・深すぎるレシピ・大きすぎるレシピで理由が出る。枠の外へのドロップでページが替わらない。右ボタンで囲みが始まらない
- **SC-806**（FR-817〜FR-820）: 既存のテストがすべて通る。版は 1.26

## Assumptions

- Worker の描画に時間の上限は設けない（大きな書き出しは長くかかることがあり、誤って止める害の方が大きい。落ちたときは FR-805 で知らせる）
- 写真を 2 枚持つぶんのメモリ（Worker 2 つ × 2 枚）は、今の「CPU の数 − 1」個 × 1 枚より十分少ない
