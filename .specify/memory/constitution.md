# 変貌世界 Constitution

## Core Principles

### I. テストファースト (NON-NEGOTIABLE)
- すべての機能は、実装より先に自動テストを書かなければならない（MUST）。
- 手順は Red（テストが失敗する）→ Green（最小限の実装で通す）→ Refactor（整理する）を守る。
- テストが失敗している状態のコードを main ブランチに取り込んではならない（MUST NOT）。
- 不具合を修正するときは、その不具合を再現するテストを先に追加しなければならない（MUST）。

理由: 品質をテストで担保することを、このプロジェクトの最優先事項とするため。

### II. ロジックと UI の分離
- 業務ロジック・データ処理は UI フレームワークに依存しないモジュールに置かなければならない（MUST）。
- UI 層はロジックを呼び出して表示するだけの薄い層に保つ（SHOULD）。
- ロジック層のテストは、画面を起動せずに実行できなければならない（MUST）。

理由: デスクトップアプリは UI の自動テストが重くなりやすいため、テストしやすい部分を最大化する。

### III. 端末内で完結するブラウザアプリ
- アプリはブラウザで動作し、画像処理はすべて利用者の端末内で行わなければならない（MUST）。
- 主な検証環境は Windows 11 上のデスクトップ版ブラウザとし、そこで正しく動くことを必須とする（MUST）。
- 起動手順は、開発者でない利用者でも実行できる形で提供する（MUST）。
- サーバー公開・アカウント・クラウド保存は、仕様で明示的に要求された場合のみ行う（MAY）。

理由: 画像を外部へ出さずに済み、利用環境を絞ることで検証範囲を明確にできる。

### IV. ユーザーデータの保護
- ユーザーのデータはローカルに保存し、明示的な同意なく外部へ送信してはならない（MUST NOT）。
- 保存処理は、途中で失敗してもデータ全体が壊れない方式で行う（MUST）。
- データ形式を変更するときは、既存データの移行処理とそのテストを用意する（MUST）。

理由: デスクトップアプリにおいてデータ消失は最も深刻な品質問題であるため。

### V. シンプルさ (YAGNI)
- 仕様に書かれていない機能・抽象化・設定項目を先回りして作ってはならない（MUST NOT）。
- 依存ライブラリの追加は、必要性を plan に記載したうえで行う（MUST）。
- 複雑な設計を採用する場合は、より単純な案を却下した理由を plan に記載する（MUST）。

理由: コードが小さいほどテストしやすく、壊れにくい。

### VI. 決定的な再現性と基準の保護
- 同じ入力・設定・アルゴリズム版からは、同じ結果が得られなければならない（MUST）。
  乱数は seed から導出し、描画処理の中で `Math.random()` や現在時刻を直接使ってはならない（MUST NOT）。
- 出力解像度・処理順・タイル分割によって乱数の消費位置が変わってはならない（MUST NOT）。
- 承認済みの基準コード・基準画像を変更してテストを通してはならない（MUST NOT）。
- 数値の合格と見た目の合格は別物として扱い、未評価の見た目や未測定の性能を合格と記録してはならない（MUST NOT）。
- アルゴリズムや保存形式を変えるときは版を上げ、旧版を新しい式で黙って処理してはならない（MUST NOT）。

理由: 作品を同じ形で呼び戻せることと、承認済みの基準を守ることがこのアプリの信頼の土台であるため。

## 技術的制約

- 言語・フレームワーク・UI 技術は、機能ごとの仕様に基づき `/speckit-plan` の段階で選定し、
  選定理由を plan に記録する。
- 選定する技術は次を満たさなければならない（MUST）:
  - Windows 11 上のデスクトップ版ブラウザで、端末内処理のみで動作するアプリを構築できること
  - 自動テスト（単体テスト）の仕組みが標準的に用意されていること
  - 単一のコマンドでテストを実行できること
- 一度採用した技術スタックの変更は、憲法の Governance に従った改訂として扱う。

## 開発ワークフローと品質ゲート

- 機能開発は Spec Kit の流れに従う:
  `/speckit-specify` → （必要に応じて `/speckit-clarify`）→ `/speckit-plan` → `/speckit-tasks`
  → `/speckit-implement`。
- 仕様（spec）には、受け入れ条件をテスト可能な形で記述しなければならない（MUST）。
- tasks では、各実装タスクの前にそれを検証するテストタスクを配置しなければならない（MUST）。
- 機能を完了とみなす条件:
  1. すべての自動テストが成功している
  2. spec の受け入れ条件がすべてテストで確認されている
  3. Windows 上のブラウザで実際にアプリを起動し、主要な操作を確認している
- 各機能は専用のブランチで開発し、上記の条件を満たしてから main に取り込む。

## Governance

- 本憲法は、このプロジェクトにおける他のあらゆる開発方針・慣習より優先される。
- 改訂する場合は `/speckit-constitution` を使い、変更内容と理由を記録する。
- バージョンはセマンティックバージョニングに従う:
  - MAJOR: 原則の削除、または互換性のない再定義
  - MINOR: 原則・セクションの追加、または指針の大幅な拡充
  - PATCH: 表現の明確化、誤字修正など意味を変えない修正
- plan および実装のレビュー時には、本憲法の各原則に違反していないかを確認しなければならない（MUST）。
  違反がやむを得ない場合は、その理由を plan の複雑性の記録欄に明記する。
